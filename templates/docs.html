Шинэчилсэн админ бүтэц (2026-05)

Хуудаснууд гурван үндсэн хэсэгт цэгцэрсэн. Хуучин URL-ууд ажиллаж байгаа ч сайдбараас сонгох замаар шинэ хэсгүүдийг ашиглахыг зөвлөе:

  • Өдөр тутмын ажил — Dashboard, Ажлын даалгавар (Inbox + Leads + Issues нэгтгэсэн 5 таб), Message Logs.
  • Бизнесийн удирдлага — Ерөнхий мэдээлэл / Бизнесийн нэгжүүд / Ажилтнууд. Нэгжийн нэр дээр дарж тухайн нэгжийн сургалт/үйлчилгээ/бүтээгдэхүүнийг шууд удирдана.
  • Ботын удирдлага — AI сургалт / Handover түлхүүр үгс / FAQ (+ чатнаас гарсан асуултууд) / Ботын тохиргоо.
  • Шинэ боломж: Course / Service / Product бүрд олон линк (description / URL / note) нэмж болно. FAQ хэсэгт OpenAI ашиглан жинхэнэ чатнаас гарсан асуултуудыг автомат бүлэглэх боломж.

Шинэ: Технологийн мэдлэггүй админд зориулсан бүрэн заавар — AI Сургалт (заавар). Хүсэлт явуулахаасаа өмнө талбар бүрийн утга, дүрэм, жишээг харах боломжтой.

1. Танилцуулга

Magic Bot бол Facebook Page чатанд ирсэн мессежид AI-аар автоматаар хариулдаг систем. Та энэ админ панелаас ботын зан төлвийг тохируулж, ажлын даалгавар (work tasks)-аа удирдаж, шаардлагатай үед өөрөө гар оруулж болно.

Гол санаа: бот энгийн асуултанд хариулна, тодорхойгүй эсвэл өндөр үнэ цэнэтэй асуултанд ажилтанд дамжуулна (handoff), Telegram-аар тантай холбогдоно. Та бэлэн болсон үед "Хариуцах" товчоор яриаг өөрөө авч болно.

Сайдбарын бүтэц: Өдөр тутмын ажил (Dashboard / Ажлын даалгавар / Мессежийн түүх) · Бизнес & бот (Бизнесийн удирдлага / Ботын удирдлага) · Систем.

2. Хяналтын самбар

Үндсэн үзүүлэлтүүд:

  • Leads — утсаа үлдээсэн нийт лидийн тоо.
  • Open Issues — шийдэгдээгүй handoff болон бусад асуудал.
  • Hot Prospects — үнэ асуусан, бүртгүүлэх хүсэлтэй болсон ч утсаа үлдээгээгүй хэрэглэгчид.
  • System health — OpenAI / Facebook / Telegram холболт тус бүрийн төлөв.

3. Ажлын даалгавар (/admin/work-tasks)

Өмнөх Inbox / Лидүүд / Асуудлууд гэсэн гурван хуудас энэ нэг хуудаст таб болж нэгдсэн. Таб бүр:

  • Халуун сонирхогч — үнэ/ready үе шатанд орсон ч утсаа өгөөгүй хэрэглэгчид. Мөр бүрт зөвхөн 2 товч: "Лид болгох" (Лидүүд таб руу шилжүүлж, статусыг "Шинэ" болгоно) эсвэл "Орхих". "Орхих" дарахад орхих шалтгаанаа заавал бичих цонх гарна.
  • Лидүүд — утсаа үлдээсэн бүх лид (хайлт, ангилал, CSV экспорт). Шинэ лид "Шинэ" статусаас эхэлдэг. Статусыг "Орхих" болгоход мөн шалтгаан заавал асууна (бусад статус өөрчлөлтөд асуухгүй). Админд "Хуучныг цэвэрлэх" товч — 60+ хоногийн хуучин чат болон хаагдсан лидийг бүрмөсөн устгана.
  • Нээлттэй асуудлууд — бүх нээлттэй issue. Тус бүрт Хариуцах ба Шийдэх товчтой. "Шийдэх" дарахад тэмдэглэл нэмэх боломжтой (заавал биш) — хэрхэн шийдсэнээ бичиж болно.
  • Удаан асуудлууд — INBOX_AGING_HOURS (анхдагч 12)-аас удсан нээлттэй issue-ууд.
  • Бот зогссон — ботыг чимээгүй болгосон хэрэглэгчид. Энд автоматаар (ажилтан FB inbox-оос хариулсан) эсвэл гар аргаар (Хариуцах / "Ботыг 30 мин зогсоох") зогссон хүмүүс орно. "Bot асаах" товчоор шууд сэргээнэ.
  • Орхисон — орхисон бүх сонирхогч ба лидийг орхих шалтгаантай нь жагсаасан архив. Мөр бүрт "Сэргээх" товч андуурч орхисон хүнийг буцааж идэвхжүүлнэ (статус "Шинэ" болно). Зөвхөн сүүлийн ~60 хоног харагдана (цэвэрлэгээгээр устдаг); бүрэн түүх audit log-д үлдэнэ. Шалтгаан нь тухайн хүний ярианы (👁) хуудсанд бас харагдана.

Хуучин /admin/inbox, /admin/leads, /admin/issues URL-ууд энэ хуудас руу 301 redirect-ээр шилжүүлэгдсэн.

4. Мессежийн түүх (/admin/logs)

Сүүлийн 100 мессежийг хугацааны эсрэг дарааллаар харуулна. Pagination нь before_id cursor ашигладаг. Хэрэглэгчийн нэр дээр дарж ярианы дэлгэрэнгүй (/admin/users/<id>/conversation) рүү очно.

5. Бизнесийн удирдлага

Сайдбараас "Бизнесийн удирдлага" дээр дарвал гурван таб гарна:

5.1 Ерөнхий мэдээлэл (/business-management/general)

Гол оффис, төвийн нэр/имэйл/утас/хаяг, бүртгэлийн нийтлэг форм URL. Хуучин Settings хуудсаас тэдгээр талбарууд энд шилжсэн. Бот хариултдаа эдгээрийг иш татаж ашиглана.

5.2 Бизнесийн нэгжүүд (/business-management/units)

Magic Choice (сургалт), Magic Consulting Audit (аудит, татвар), Magic Cloud (програм) — бизнесийн нэгж бүрд "Хариулах / Чиглүүлэх" зан, төрөл (Course / Service / Product), холбоо барих, тайлбар бичнэ. Нэгжийн нэр дээр дарж дотогш орвол:

  • Нэгжийн дэлгэрэнгүй карт (collapsible)
  • Зүйлсийн (item) хүснэгт: бүтээгдэхүүн / үйлчилгээ / сургалт төрлөөрөө ялгагдана
  • Олон линкийн засварлагч: зүйл бүрд хэдэн ч холбоос (Тайлбар / URL / Тэмдэглэл) нэмж болно. Жишээ: Magic Finance програмд татах хуудас, гарын авлага, license сунгуулах форм гэх мэт холбоосуудыг нэг дор оруулна.

Бот эдгээр линкийг тохирох асуултын хариултанд иш татна.

5.3 Ажилтнууд (/business-management/employees)

Багш / зөвлөх / хариуцагчдын жагсаалт. Бот "Х асуудлыг хэн хариуцдаг вэ?" гэх мэт асуултанд эндээс эшилж хариулна. Идэвхгүй болгох тохиргоо нь түр чөлөөтэй гишүүнийг ботод үзүүлэхгүй байх боломж.

6. Ботын удирдлага

Сайдбараас "Ботын удирдлага" → анхдагчаар Ботын тохиргоо таб нээгдэнэ. Бусад таб:

6.1 AI сургалт (/bot-management/training)
  • Persona — ботын дүр / дуу хоолой (зөвхөн супер админ засна).
  • Нэмэлт тайлбарууд (★ Snippets) — бодит чатанд алдаа гарах бүрд нэг шинэ snippet нэмж шууд засна. ★ Өндөр хэлбэрийн snippet нь системийн хариултын эхэнд орж илүү жинтэй нөлөөлнө.
  • AI харж буй prompt — "Үзэх" товч нь яг одоо ботод очиж буй бүхэл бүтэн системийн заавар (system prompt)-ийг гаргана. Шинэ snippet эсвэл FAQ хэрхэн нэгтгэгдсэнийг алхам алхамаар харах хэрэгсэл.
  • Нийцлийн шалгалт — "Ажиллуулах" товч дарвал FAQ / Persona / Snippet-д дурдсан үнэ, утас, URL нь Course / Product / Service / Бизнес нэгжийн жагсаалттай таарч байгаа эсэхийг автоматаар шалгана. Хуучирсан огноотой Сургалтыг (end_date өнгөрсөн ангиуд) мөн зэрэг харуулна. Жижиг "эрүүл мэндийн" шалгалт — 7 хоног тутамд ажиллуулж байх нь тохиромжтой. Дэлгэрэнгүйг AI Сургалт (заавар) 3.3 хэсэг-ээс үзнэ үү.
6.2 Дамжуулах түлхүүр үгс (/bot-management/handover)

Хэрэглэгчийн мессеж тодорхой үгстэй таарвал шууд handoff гаргадаг. Explicit — "ажилтантай ярьмаар", "huntei" гэх мэт. Frustration — "болохгүй байна", "ойлгохгүй" гэх мэт. Латин үсгээр бичсэн хувилбарууд (huntei, operator, menejer) бас орсон байгаа.

6.3 FAQ (/bot-management/faqs)
  • Гар хийсэн FAQ — админ бичсэн Q/A хосууд. Бот системийн заавартай хамт уншина.
  • Чатнаас гарсан жинхэнэ асуултууд — LLM (gpt-4o-mini) сүүлийн 30 хоногийн хэрэглэгчийн асуултуудыг сэдэвчилсэн бүлэгт оруулж харуулна. Долоо хоног бүр автомат шинэчлэгдэх ба (ENABLE_CHAT_CLUSTERING=true орчны хувьсагч идэвхтэй үед), "Шинэчлэх" товчоор гараар ажиллуулж болно. "FAQ болгох" товчоор тухайн бүлгийг гар FAQ-д шилжүүлнэ.
6.4 Ботын тохиргоо (/bot-management/settings)
  • Илрүүлэх мэдрэмж — handoff хэр амархан гарахыг тохируулна (conservative / balanced / aggressive).
  • Ботыг чимээгүй болгох цаг — анхдагч 0 цаг (advisory mode: handoff гарсан ч бот үргэлжлүүлэн тусална). Тодорхой тоо тавивал handoff гармагц автоматаар ботыг тэр цагт зогсооно.
  • Telegram chat ID-ууд — мэдэгдэл хүлээн авах ID-ууд. "Туршиж үзэх" товчоор шууд шалгана.
  • Ажлын цаг — Off-hours handoff үед Telegram-д 🌙 тэмдэгтэй мэдэгдэх ба хэрэглэгчид маргааш холбогдоно гэсэн хариу автоматаар явна.
  • Халуун сонирхогчийн funnel шат — анхдагч pricing,ready.
  • Auto-comment блок — Facebook Page постонд автомат сэтгэгдэлд ашиглах текст.

7. Систем

Сайдбараас "Систем" → анхдагчаар Админ хэрэглэгчид таб нээгдэнэ:

  • Админ хэрэглэгчид — admin / super_admin эрх бүхий хэрэглэгчдийн жагсаалт. Нууц үг хамгийн багадаа 12 тэмдэгт. Нууц үгээ мартвал Render-ийн RESET_ADMIN_USERNAME ба RESET_ADMIN_PASSWORD орчны хувьсагчид утга өгч, дахин deploy хийгээд буцааж устгана.
  • Үйлдлийн түүх (Audit log) — нийт админ үйлдлүүдийн append-only лог.
  • Баримт бичиг — энэ хуудас (Манул + Тex Spec).

8. Handoff урсгал

Гурван төлөв:

  1. Энгийн — handoff issue алга, бот ердийнхөөрөө ажиллана.
  2. Зөвлөмжийн горим (advisory) — handoff issue нээлттэй боловч staff хариуцаагүй байна. Бот хэрэглэгчтэй үргэлжлүүлэн ярилцана (каталогийн дэлгэрэнгүй, FAQ хариулна) гэхдээ хэрэглэгчийг "manai mergejilten" руу ДАХИН чиглүүлэхгүй. Telegram-аар админ мэдэгдсэн.
  3. Staff хариуцсан — бот тогтоосон хугацаагаар чимээгүй болсон. Энэ үед бот огт хариулахгүй; staff Facebook Page Inbox-оос шууд харилцана.

Бот зогсох (mute) 3 арга:

  • Автомат (хүн дамжуулалт) — ажилтан FB Page inbox-оос хэрэглэгч рүү бичихэд Facebook message_echoes үйл явдал илгээж, бот тухайн хэрэглэгчид HUMAN_TAKEOVER_MUTE_MINUTES (30) минут чимээгүй болно. Идэвхжүүлэхийн тулд Ботын тохиргоо → "Webhook тохиргоог шалгаж засах" (нэг удаа). Анхны мессежид бот хэвийн хариулна; зогсолт нь ажилтан орсны дараах хариултуудыг л чимээгүй болгоно.
  • Гар аргаар — яриаг харах хуудаснаа "Ботыг 30 мин зогсоох" / "Ботыг асаах" товч (нөөц арга).
  • Staff "Хариуцах" — handoff issue-г "In Progress" болгож бот N цагаар чимээгүй болно.

Бусад ажиллагаа:

  • Handoff гарвал → AdminIssue үүснэ, Telegram мэдэгдэнэ, хэрэглэгчид "ажилтан удахгүй холбогдоно" гэж хариу явна. Бот advisory mode-д ороод үргэлжлүүлэн тусална.
  • Staff "Шийдэх" → issue resolved болж, бот шууд асна (mute timer хүлээхгүй).
  • Mute timer дуусвал ч бот сэргэнэ.

9. Алдааны шийдэл

Бот хэрэглэгчид хариулахаа больсон

Ажлын даалгавар → Бот зогссон таб дээр шалга. "Bot асаах" товчоор шууд сэргээ. Эсвэл тухайн хэрэглэгчийн handoff issue-г "Шийдэх" товчоор хаа — бот автоматаар асна.

Шинэ handoff гарсан ч Telegram мэдэгдэхгүй байна

Ботын удирдлага → Ботын тохиргоо → "Туршиж үзэх" товчийг дар. Алдаа гаргавал token / chat ID тохиромжгүй гэдгийг тодорхой хэлнэ.

Нэр "Unknown" гэж харагдаж байна

Facebook апп Development mode-д байгаа бол ажилтан бус хэрэглэгчдийн нэр татагдахгүй. App Review дууссаны дараа Ажлын даалгавар → Лидүүд таб → "Нэр шинэчлэх" товчоор нийтийг шинэчилнэ.

Бот зөв хариулж чадахгүй болсон

Алдаа гарах бүрд Ботын удирдлага → AI сургалт → Нэмэлт тайлбарууд-д нэг шинэ snippet нэм. Бодит чатнаас гарсан асуултын хэв маягийг тусгай хариулттай харилцуулж бичих нь хамгийн үр дүнтэй сургалтын арга.

Тийм — бүгд 301 redirect-ээр шинэ хуудсууд руу шилждэг. Хэдэн хувилбарын дараа эдгээрийг бүрэн устгана.

1. Overview

Magic Bot is a single-codebase, multi-tenant Flask app that connects a Facebook Page to OpenAI's Chat Completions API to auto-reply in Mongolian. One service instance backs one Facebook Page; multiple businesses are served by cloning the Render service and overriding a small set of branding-related environment variables.

2. Stack

LayerTech
Web frameworkFlask 3 + Flask-Login + Flask-SQLAlchemy
LLMOpenAI gpt-4o-mini via openai SDK
MessengerFacebook Graph API v18.0 (webhook + Send API)
AlertsTelegram Bot API sendMessage
DBSQLite by default, Postgres-compatible via SQLAlchemy URI
FrontendBootstrap 5 + Bootstrap Icons (CDN)
HostingRender (Free or paid web service)
Processgunicorn via Procfile

3. Multi-tenancy

All branding/persona is environment-driven so the same code runs for any business: TRAINING_CONTENT, BOT_PERSONA, COMPANY_*, PRODUCT_NAME, SEED_DEFAULTS. To onboard a new bot: clone the Render service, point it at a new Facebook App + Page, override the env vars, set SEED_DEFAULTS=false so it doesn't inherit Magic's catalog.

4. Data model

5. Routes layout

routes/admin/ is a package split into focused modules:

  • routes/admin/auth.py — login / logout
  • routes/admin/work_tasks.py — dashboard, work tasks (formerly inbox / leads / issues), logs, conversation viewer, ops APIs (telegram test, name backfill, classify, take_over)
  • routes/admin/business.py — business-management routes (/business-management/{general,units,employees}, /business-units/<id>), legacy /admin/{courses,services,products,team,business-lines} POST handlers
  • routes/admin/bot.py — bot-management routes (/bot-management/{training,handover,faqs,settings}), training-snippet CRUD, chat-clustering trigger, promote-cluster-to-faq
  • routes/admin/system.py — admin user management, audit log, docs, settings (deprecated), /admin/api/run-migration, /admin/api/seed-default-links, /admin/api/seed-discovery-snippets

Endpoint names stay flat (no Flask Blueprint prefixes) so existing templates' url_for('dashboard'), url_for('login') etc. don't need updating.

6. Webhook lifecycle (async)

The webhook ACKs Facebook in <1s and generates the reply in a background worker. A fast 200 stops Facebook retrying the delivery on slow hops / cold starts — those retries used to inflate the rate limiter and double-send replies. The reply model is gpt-5.3-chat-latest (REPLY_MODEL); background jobs stay on gpt-4o-mini.

Synchronous half — POST /webhook (routes/webhook.py:webhook()):

  1. Verify X-Hub-Signature-256 = HMAC-SHA256(raw body, FACEBOOK_APP_SECRET). Reject 403 on mismatch.
  2. Echo handling (message_echoes): every Page-sent message echoes back. Bot sends carry metadata=BOT_ECHO_TAG → ignored. An untagged echo = a human agent replied in the Page inbox → human_takeover_pause() sets bot_muted_until = now + HUMAN_TAKEOVER_MUTE_MINUTES (30). Echoes always continue (never enter the reply pipeline).
  3. Get-or-create FacebookUser by PSID; resolve name via FB Graph (or ask-for-name path).
  4. Classify session state; idempotency claim: persist the inbound row keyed by the unique Message.mid. A retried delivery (same mid) raises IntegrityError and is dropped here — before the rate limiter and before any reply.
  5. Per-sender sliding-window rate limit (default 5 msg / 60s). Over-limit = silent drop (no throttle text). Retries can't trip it because they're already deduped above.
  6. Advance funnel stage (no regression); name-capture + phone-capture (a captured lead starts at lead_status='new').
  7. Mute gate: if bot_muted_until > now (staff/human takeover), silent-drop. Auto-clear expired mutes.
  8. enqueue_background(process_inbound_reply, fb_user.id, message_text, session_state) → return 200.

Asynchronous half — process_inbound_reply() (background thread, own app context + DB session):

  1. Re-check mute; send mark_seen + typing_on sender actions (responsive feel).
  2. is_in_handoff() → handoff_pending; keyword should_handoff() → trigger_handoff(send_user_message=False) on match.
  3. Build prompt, call REPLY_MODEL with last 10 messages, max_completion_tokens=REPLY_MAX_TOKENS (500). gpt-5.x rejects temperature/max_tokens.
  4. Strip the internal [HANDOFF] marker (knowledge-gap deferral via the defer_to_staff tool).
  5. Pre-send mute re-check: db.session.rollback() (drop the stale WAL snapshot) then re-read bot_muted_until — if a human took over mid-generation, suppress the reply.
  6. Persist outbound, send via FB Send API (tagged with BOT_ECHO_TAG).
  7. Response-based handoff (bot_response_implies_handoff / knowledge-gap); then classify_user_topics().

enqueue_background runs inline under TESTING (deterministic; in-memory SQLite is per-connection). A background failure = no reply, logged, no crash, no FB retry.

7. Handoff lifecycle

Three explicit states keyed off open AdminIssue (handoff_pending) and bot_muted_until:

  1. Normal — no open handoff issue, bot does its full discovery + sales loop.
  2. Advisory mode (handoff_pending=True, bot_muted_until=null) — open handoff AdminIssue exists. Bot keeps replying with full catalog knowledge, but the injected HANDOFF_ADVISORY_RULE forbids re-routing or re-asking for phone (the customer is already in the queue). Each reply may end with a brief "ажилтан холбогдоно" reminder.
  3. Staff takeover (bot_muted_until > now) — staff clicked "Хариуцах" on the Work Tasks page with a duration (default 4h). Bot is silent so staff can chat directly via Facebook Page Inbox.

Sensitivity tiers (handoff_sensitivity setting):

  • conservative (default) — explicit stem matches (ажилтан / оператор / менежер / хүнтэй / huntei / human / etc.) + business-line refer matches.
  • balanced — adds frustration phrases (болохгүй байна / ойлгомжгүй / гомдол / etc.).
  • aggressive — adds repeated-question detection (same message 3× in 1h).

Stems are deliberately short to defeat Mongolian agglutinative suffixes: 'ажилтан' catches ажилтантай / ажилтанд / ажилтны / ажилтнаас, etc. Latin transliterations are seeded (huntei, operator, menejer, azhiltan) so customers typing without the Mongolian keyboard still trigger handoff.

trigger_handoff(send_user_message=False) exists for the response-based path so a bot that already sent a deferring reply doesn't double-message the user. Auto-mute on handoff is gated by mute_duration_hours setting (default 0 = advisory only; set >0 for immediate silence). Staff "Шийдэх" auto-unmutes — closing the issue restores the bot.

Response-based detection: bot_response_implies_handoff(reply_text) returns the matched phrase if the bot's own reply says it's deferring to staff. Phrases checked: 'мэргэжлийн ажилтан', 'манай ажилтан танд / удахгүй', 'ажилтан танд / тантай эргэж', 'ажилтантай холбог', 'тусгай ажилтан'.

7. Funnel + session

Funnel: curious → exploring_courses → pricing → ready. Detection is keyword-based, never regresses. Stage drives a per-stage prompt section guiding the bot's tone (informational at curious, registration push at ready).

Session classified from time since last message: new / active (<2h) / gap (2-24h) / returning (24h+). Drives greeting behaviour (don't say "Сайн байна уу" mid-active conversation).

8. Notifications

Two channels, both optional:

  1. Telegram — send_telegram_notification(text) reads TELEGRAM_BOT_TOKEN from env, chat IDs from the telegram_chat_ids setting (comma-separated; group IDs are negative). Fires on every handoff. Silent no-op if the token env var or the chat IDs setting is empty — the handoff itself still completes, only the Telegram leg is skipped. Per-recipient errors are logged but never block the handoff.
  2. In-dashboard — every admin page polls /admin/api/handoff-poll every 15s; localStorage tracks the last-seen issue id. On new id, plays a beep via Web Audio API (oscillator → gain → destination, no asset file) and shows a red toast.

10. Deployment

  1. Create a Render web service from this repository. Procfile points gunicorn at app:app.
  2. Set the required env vars. SQLite without a persistent disk gets wiped on every redeploy — for production attach a Render persistent disk at /var/data and set SQLALCHEMY_DATABASE_URI=sqlite:////var/data/magic_bot.db.
  3. In the Facebook Developer Console: webhook URL = https://<render-url>/webhook, verify token = your VERIFY_TOKEN, subscribe the page to messages events.
  4. For Live mode: submit pages_messaging for Advanced Access via App Review. Without it, only people with app roles can chat with the bot and have their profiles resolved.
  5. Privacy policy URL = https://<render-url>/privacy.

11. Schema migration

Two layers, both idempotent:

  1. Alembic via Flask-Migrate — proper revision-tracked migrations live at migrations/versions/. Current HEAD: 0003_chat_question_clusters. Standalone migrations/env.py doesn't import the Flask app, so alembic upgrade is fast even on cold start.
  2. Bootstrap script — scripts/apply_phase_1_migration.py is a pure sqlite3 runner that applies the same changes without SQLAlchemy / Alembic startup overhead. app.py:init_db() calls it via _run_pending_migrations() on every boot. Fail-soft (logs traceback, doesn't crash init_db) so a broken migration doesn't 502 the whole service. Includes a self-healing sanity check: if alembic_version claims HEAD but canary columns (product_link.description, business_line.product_type) are missing, force a re-run.

Manual trigger: POST /admin/api/run-migration (logged-in admin) returns the bootstrap script's output as plain text. Use this if a deploy left the schema in an unexpected state.

Legacy ensure_schema() still exists in services.py for backward compatibility — adds columns introduced before Alembic was wired up (funnel_stage, last_nudge_at, bot_muted_until, conversation_topic, last_mute_ack_at). New schema changes go through Alembic, not ensure_schema.

11b. Chat-question clustering

services.cluster_chat_questions() pulls the last 30 days of Message rows where sender='user', filters via a Mongolian-interrogative heuristic to drop one-word acknowledgements, sends up to 400 deduplicated phrasings to gpt-4o-mini with response_format={'type': 'json_object'}. The model groups them into 5-15 themes with title, representative_question, sample_questions, count.

Results wholesale-replace the unpromoted chat_question_cluster rows; rows with promoted_to_faq_id set are preserved across runs (those clusters are already FAQ). Fail-soft: any error returns 0 rather than crashing the weekly thread.

Promote flow: POST /admin/api/promote-cluster-to-faq creates a curated FAQ row from a cluster's representative_question + admin-typed answer, then sets promoted_to_faq_id so the cluster doesn't reappear on next clustering.

12. Security

  • Webhook signature verification — HMAC-SHA256 against the raw body. Mandatory in Live mode.
  • Rate limiting — sliding window per sender (in-memory; for multi-worker swap to Redis).
  • Admin password policy — minimum 12 characters, hashed with Werkzeug's PBKDF2-SHA256.
  • Role tiers — destructive admin actions (create / delete / role change / password reset) require super_admin.
  • Last super_admin protection — can't delete or demote the last super_admin or the last admin.
  • Auto-self-heal — if a deployment has admins but none are super_admin, the oldest is promoted on boot.

13. Known limitations

  • SQLite + multi-worker gunicorn — fine for one or two workers under low load; under higher concurrency move to Postgres.
  • Rate-limit state is in-memory — each gunicorn worker has its own counter. Scale-out requires Redis.
  • OpenAI cost per inbound message — every non-handoff, non-muted message hits the API. Aggressive rate limits, business-line refer, and snippet quality are your levers.
  • Name lookup depends on FB permissions — Development mode + non-app-role users → name stays "Unknown" until pages_messaging gets Advanced Access.
  • Polling auto-commenting is off by default — turning it on with multiple gunicorn workers will produce duplicate comments. Run one worker if you enable it.
